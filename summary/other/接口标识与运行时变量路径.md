# 接口标识与运行时变量路径

更新时间：2026-11-03 10:36

## 相同字段名不代表相同标识体系

一次 USB 弹出问题中，查询接口返回系统变量 UUID，前端将其作为写接口变量标识使用，而写入侧需要变量路径。字段都叫 id，不代表它们属于同一套命名空间。

| 标识 | 指向什么 | 不应混同于 |
| --- | --- | --- |
| 运行时系统变量 UUID | 系统变量定义 | 文件系统 UUID、设备名 |
| 运行时变量路径 | 写接口需要解析的变量 | OS 文件路径、挂载点 |
| 文件系统 UUID | 文件系统实例的标识 | 运行时变量 UUID |
| /dev/sdb1 | 当前枚举中的分区设备节点 | 稳定设备身份 |
| /mnt/disk0 | OS 挂载点 | 前端分区入口或变量路径 |

## 修复应对齐接口契约，不要全局替换

1. 从消费者倒推：明确写入接口实际解析 UUID、索引还是路径。
2. 找查询字段的生成链路，尽量复用已有 ID 到路径的解析函数。
3. 只转换需要满足写入契约的输出；内部按 UUID 读状态的代码保留原语义。
4. 检查标识的其他消费者、缓存和刷新机制，不能仅凭编译通过判定兼容。
5. 明确空值行为：映射未初始化或不存在时返回空串，可能让 JSON 的 omitempty 隐去字段，导致前端缺少可写标识。

原案例复用 GetSystemVariablePathByID，将四个 USB 槽位的响应 id 转为变量路径；挂载判断仍依赖各槽位 mount 状态，文件访问依赖分区名及路径。故标识转换本身不会产生额外挂载条目。

## 需要额外检查的生命周期边界

- 默认解析函数是否在启动期返回空值，真正解析器何时注入。
- 解析器所引用的全局运行时是否与调用方传入的运行时一致。
- 对象首次创建后是否缓存旧 id；后续刷新只更新容量时，空标识可能长期保留。
- 多设备、多分区、拔插与工程重载后，分区名和变量路径是否仍正确对应。
- 缺失数据是否触发清理；直接跳过缺失槽位可能留下旧条目，但这不等于已证实发生。

## 验证要分层报告

静态检查证明代码路径与依赖关系；本地测试证明特定输入行为；现场接口和设备状态才能证明实际弹出效果。依赖导致无法编译，不等于测试断言失败；用户报告联动弹出，也不足以推导底层卸载调用的具体实现。

修改标识字段语义属于接口兼容性变化，应核对其他客户端，不能将“当前仓库未发现依赖 UUID”扩写成“所有消费者均无影响”。
