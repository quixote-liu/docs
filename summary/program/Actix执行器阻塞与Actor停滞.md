# Actix 执行器阻塞与 Actor 停滞

更新时间：2026-11-06 02:16

Actix Actor 在 Arbiter 的执行环境中被轮询。异步任务只有在主动挂起并把控制权还给执行器时，其他任务才有机会继续运行。若一个 future 在 poll 期间执行长时间同步工作，或同步代码进入高 CPU 循环，该 Arbiter 上的 Actor 消息、定时器和其他异步任务都会延迟；进程仍可能响应由其他线程承载的工作，因此“HTTP 接口可调用”不等于某个 Actor 正常推进。

在 Linux 输入流场景中，异步 API 不代表执行逻辑不会占用执行器。底层流的 poll/状态补偿代码仍可能在一次 poll 中做大量同步工作。若流在 `SYN_DROPPED` 后陷入循环，问题会扩散到共享同一 Arbiter 的 Actor。

处置原则：

- 将可能阻塞或执行时间不可控的系统调用、外部命令和复杂采集从 Actor handler 移出；使用 `spawn_blocking`、独立线程或独立 runtime，并为结果回传设置超时和背压策略。
- 对有缺陷风险的设备流单独隔离执行环境；下游只传递归一化、低流量的状态事件。
- 用 Actor 自身的低频心跳判断调度是否仍在推进。由不共享该执行器的独立线程/进程监督心跳，超时后交给 systemd 重启；在故障进程内部依赖同一个 Actor 发起恢复并不可靠。
- 心跳能发现和恢复停滞，不代表定位或修复了忙循环。应结合线程 CPU、core/perf 用户态栈和精确匹配的调试符号定位根因。

具体的 evdev 0.12.1、`SYN_DROPPED` 和触摸屏多 ABS 轴案例见[Linux 触摸事件溢出导致系统变量推送停滞](../../notes/0003-Linux触摸事件溢出导致系统变量推送停滞.md)。
