# 历史数据和数据集支持分段存储

更新时间：2026-10-23 16:12

场景：下位机需要让历史采集数据和普通数据集按配置写入独立 SQLite 文件，支持单文件限额、分段切换、历史查询、趋势图、备份及模拟运行。本文根据 2026-10-19 的功能提交和 10 月中下旬 Codex 交流整理。

## 最终实现脉络

- 历史采集表仍是**普通数据集表**；历史策略通过 `tableId` 关联它，不另造一套“历史数据集”存储模型。采集继续复用数据集的启停、触发、周期和连接状态判断。
- SQLite 模式下，将启用文件存储的表拆成单表数据源 `data_<表名>`，复用原有表迁移和 CRUD；元数据保存在 `data` 库的 `__dataset_file_storage_meta`。PostgreSQL 模式下将 Runtime 历史采集表合并到 `data`，不拆文件。
- 元数据以稳定 `tableId` 关联表，用 `Current` / `Closed` 区分当前文件和封存文件。切段先准备新文件及表结构，再提交元数据变更、替换当前连接。文件名来自静态配置或绑定变量，分段后缀决定切段的时间粒度。
- 单文件模式达到记录数或有效容量限制后，清理旧记录并复用空闲页；分段模式达到限制后封存当前文件、创建新文件。最大文件数包含 `Current`，但删除时只选择最旧的 `Closed`；存储时长清理只作用于 `Current`。
- 历史查询在 WebGUI HTTP handler 分流到数据集查询，按历史策略和列的 `VariableId` 找表与字段；Runtime 只提供启动时恢复历史变量最新值所需的查询接口。趋势图、导出和备份也接入新文件路径。

```text
数据集表配置 → SQLite 单表数据源 → FileStorageManager → Current SQLite 文件
                                ↘ data 库元数据 ↔ Closed 文件索引
历史策略 tableId ────────────────↗
```

## 开发中形成的关键判断

| 问题 | 结论或处理 |
| --- | --- |
| 文件名与目录 | 按工程、表名和配置生成路径；动态文件名为空时回退表名；模拟模式与真实运行路径分别处理。 |
| 写入条数上限 | 普通写入只累加内存计数；接近阈值才查询真实 `COUNT`，周期任务仍校准直接脚本写入等遗漏。 |
| 容量清理 | 单文件模式用 `page_count`、`freelist_count`、`page_size` 衡量有效页面；删除旧记录后空闲页供后续插入，不每轮执行 `VACUUM`。高频宽表测试促使单文件清理预留约 20% 容量。 |
| 触发变量 | 绑定保存变量 Path，执行时解析实际索引，兼容动态索引变量；切段前要确认变量连接与状态有效。 |
| 跨层职责 | 文件路径和连接由文件管理器提供；采集器负责采集时机；HTTP handler 负责历史查询分流；Python 环境需要同步 Current 文件路径。 |

## 遇到的问题及证据状态

- 启动时管理器表数为 0、普通表出现“历史数据集连接不可用”：讨论和代码修复指向数据源拆分、初始化时机与名称匹配。最终代码通过 SQLite 拆分 / PostgreSQL 合并、按 `tableId` 找文件连接处理。具体现场需结合对应工程配置核验。
- `CURRENT_TIMESTAMP()` 被当作 SQLite 默认表达式时，建表曾报 `near "(": syntax error`。历史采集表的毫秒主键由调用方写入；不能仅凭配置字符串假定 SQLite 会生成 Unix 毫秒。
- `segmentedStorage=false` 的表到条数上限后曾错误切段。核对需求后确定：单文件清旧行，分段模式才封存和新建。
- 短时间两次触发只得到一个新分段：2026-10-21 的代码排查发现，若时间后缀生成同一目标路径，第二次切段会被跳过，且触发状态已更新。该会话未读到现场日志，所以这是**代码层面的解释，未确认现场命中**。
- `/api/variables/history` 曾报 `database disk image is malformed`。2026-10-20 会话只定位到读取分段 Current SQLite 的链路，**没有证明文件损坏根因或修复结论**；排查时应分别检查数据库完整性、WAL/SHM、切换及备份时的文件生命周期。
